# Проверка типов

Проект рассчитан на **Python 3.14**. Настройки Pyright находятся в
`pyrightconfig.json`: режим `strict`, целевая версия Python 3.14 и окружение
`.venv` в корне репозитория. Для проверки нужны зависимости приложения,
включая PyQt6, aiohttp и BeautifulSoup, а не только сам Pyright.

## Подготовка окружения

Выполняйте команды из корня репозитория.

Linux / macOS:

```sh
python3.14 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
python -m pyright
```

Windows (PowerShell, активация окружения не требуется):

```powershell
py -3.14 -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[dev]"
.venv\Scripts\python.exe -m pyright
```

Вместо установки пакета с dev-зависимостями можно установить
`python -m pip install -r requirements.txt`: этот список также содержит
зависимости приложения и Pyright. В обоих случаях используйте Python из `.venv`.

## Если редактор показывает ошибки импортов

- Выберите интерпретатор `.venv/bin/python` (Windows: `.venv\Scripts\python.exe`)
  через **Python: Select Interpreter**.
- Убедитесь, что зависимости установлены именно в это окружение:
  `python -m pip check`.
- Повторите `python -m pyright` из корня репозитория. При необходимости
  перезапустите языковой сервер редактора после установки зависимостей.

Ошибки `reportMissingImports` и связанные с ними `reportUnknown*` могут быть
следствием отсутствующих зависимостей. Не скрывайте их отключением строгого
режима или генерацией заглушек для отсутствующих пакетов. Pyright использует
типы установленных библиотек; локальные `.pylance_stubs` не требуются.

Проверка также запускается в GitHub Actions при push и pull request.

## Тесты и линтер

```sh
python -m ruff check .
python -m pytest -q
```

Тесты используют временные базы данных, не обращаются к истории из рабочей
копии и не выполняют сетевое сканирование. Проверяются изоляция пользователей,
удаление связанных уязвимостей, откат транзакции, подтверждение/отмена,
блокировка во время сканирования и обновление открытых окон. Для панели также
проверяются единственность реализации, оба маршрута навигации, жизненный цикл
задачи, управление сканированием, закрытие/выход и экспорт отчётов.

UI-тесты работают с Qt в режиме `offscreen` (без дисплея). Если системные
библиотеки Qt отсутствуют, соответствующие модули будут отмечены как пропущенные.
В GitHub Actions нужные библиотеки устанавливаются перед запуском тестов.
Для запуска только проверок базы данных:

```sh
python -m pytest -q tests/test_scan_history_database.py
```

## Где доступна очистка истории

В главном окне откройте **«Статистика» → «История сканирований»** и нажмите
**«Очистить историю…»**. После подтверждения удаляются все сканирования текущего
пользователя (включая записи за пределами показанных 100) и связанные с ними
уязвимости. Данные других пользователей, профиль и экспортированные файлы
сохраняются. Во время сканирования, паузы или завершения сохранения очистка
не выполняется; сначала дождитесь окончания задачи.

## Архитектура панели управления

Используйте только `views.dashboard_window.DashboardWindow`.
`MainWindow.show_dashboard()` — совместимый маршрут к `go_to_dashboard()`,
а не отдельная реализация окна. Не создавайте новые варианты с суффиксами
`updated`, `fixed`, `optimized` или отдельной Qt-обёрткой.

Интерфейс, правила состояния, представление событий и отчёты вынесены в
пакет `views/dashboard/`. Подробности ревизии, границы модулей и гарантии
жизненного цикла описаны в [docs/dashboard_refactor.md](docs/dashboard_refactor.md).

## Пейлоады

Добавляйте и редактируйте пейлоады только в соответствующих модулях пакета
`payloads/`, а не в конфигурации или методах сканеров. Импортируйте нужный набор
напрямую, например `from payloads.sql import SAFE_SQL_PAYLOADS`.

Разделение наборов, совместимость прежних импортов и регрессионные проверки
описаны в [docs/payloads.md](docs/payloads.md). Порядок элементов важен:
некоторые проверки используют только первые пейлоады или первый элемент для форм.
